# Authentication and Protected Routes

## 1. Authentication Architecture
ThinkWires uses HttpOnly cookie-based session tokens for candidate authentication.
- **Cookie Security**: Tokens are generated by the backend and set with `HttpOnly; SameSite=Lax; Path=/`.
- **Zero LocalStorage Token Leakage**: Sensitive JWT secrets and raw tokens are never written to `localStorage` or `sessionStorage`.
- **Automatic Hydration**: On initial application load, `App.jsx` dispatches `checkAuthSession()` to verify authentication against `/api/auth/me`.

## 2. Redux Auth Slice (`src/store/slices/authSlice.js`)

### State Shape
```typescript
{
  user: {
    id: string;
    name: string;
    email: string;
    phone?: string;
    experience?: number;
    technicalSkills?: string[];
    resumeUrl?: string;
    location?: string;
  } | null;
  isAuthenticated: boolean;
  isInitializing: boolean; // True until first /api/auth/me resolves
  loading: boolean;
  error: string | null;
  successMessage: string | null;
}
```

### Async Thunks
- `checkAuthSession()`: Sends `GET /api/auth/me` with `credentials: 'include'`.
- `loginUser({ email, password })`: Sends `POST /api/auth/login`. Sets authenticated user in Redux.
- `registerUser({ name, email, password, confirmPassword, phone })`: Sends `POST /api/auth/register`.
- `logoutUser()`: Sends `POST /api/auth/logout` clearing the cookie.
- `updateProfile(profileData)`: Sends `PUT /api/candidate/profile` to update candidate details.

## 3. Protecting Routes (`ProtectedRoute.jsx`)
```jsx
const ProtectedRoute = ({ children }) => {
  const { isAuthenticated, isInitializing } = useSelector((state) => state.auth);
  const location = useLocation();

  if (isInitializing) {
    return <div className="tw-loading-indicator">Verifying candidate session...</div>;
  }

  if (!isAuthenticated) {
    return <Navigate to={`/login?redirect=${encodeURIComponent(location.pathname + location.search)}`} replace />;
  }

  return children;
};
```

When an unauthenticated user tries to apply for a job or view their dashboard, they are seamlessly redirected to `/login?redirect=...`. Upon successful login, `LoginPage` reads the redirect search param and returns the candidate directly back to their intended application flow without losing context.
